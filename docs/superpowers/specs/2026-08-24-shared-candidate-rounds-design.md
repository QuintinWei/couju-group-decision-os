# 凑局共享候选分轮机制设计

日期：2026-08-24

## 目标

让同一房间的所有成员始终评价同一批候选，同时解决“整批都不满意却无法继续”的死路。系统最多进行三轮，每轮固定十二张共享卡片；换批由成员发起请求、房主确认执行，新一轮同时学习全体成员反馈并保留个人约束。

本次同时实现受控的“个人发现卡”：只有成员把本轮十二张共享卡全部拒绝时，系统才额外提供三张仅该成员可见的私人救援卡。成员最多提名一张进入下一轮共享候选；未经其他成员补充评价的私人卡不能成为最终结果。

## 产品规则

### 共享候选

- 同一轮内，所有成员看到相同的候选集合和基础顺序。
- 每位成员看到的通勤时间按自己的出发地计算。
- 每个人独立提交喜欢、还行、不想去，以及预算、通勤、场景偏好和可选 AI 补充。
- 只有所有真实成员都评价过的共享候选，才可以进入最终群体排序。

### 私人救援卡

- 成员把本轮十二张共享卡全部选择为“不想去”后，显示三张仅该成员可见的私人救援卡。
- 私人救援卡根据该成员的预算、通勤、场景偏好、自然语言约束、已拒绝类别和尚未出现的新类别生成。
- 成员最多提名一张，也可以三张全部拒绝并跳过。
- 全部拒绝不会阻断换批；系统记录这些负反馈，并在后续推荐中排除具体地点、降低相似类别权重。
- 被提名的私人卡只会进入下一轮十二张共享卡，必须由全体成员评价后才能进入最终群体排序。
- 私人救援卡不计入当前轮“十二张共享卡”的数量。

### 请求换批

- 成员完成本轮卡片后，可以正常提交，也可以勾选“这批都没感觉，请求换一批”。
- 请求不会立即清空其他成员进度。
- 房间页显示本轮完成数和换批请求数，例如“3/4 人完成 · 2 人请求换批”。
- 房主只有在当前已加入成员全部完成本轮后，才能确认开启下一轮。
- 如果任一成员把十二张共享卡全部拒绝，或群体计算没有任何可行候选，房主在所有人完成后可以直接开启下一轮。
- 如果已经存在共同结果，但仍有成员主动请求继续探索，结果正常展示，同时房主可以决定采用结果或开启下一轮。
- 只有房主能够真正开启下一轮；普通成员只能请求。
- 只有房主一人时，房主完成后可以直接换批。

### 三轮上限

- 第一轮：广泛探索，强调类别多样性。
- 第二轮：根据全体反馈收敛，同时保留新类别。
- 第三轮：重点补充分歧较小、通勤与预算更可行的候选。
- 第三轮仍无解时，不再无限换批，显示冲突诊断并引导放宽具体条件。

## 新一批候选构成

每轮始终生成十二张共享候选，其中至少四张是“新鲜探索”。其余八个位置先放入成员提名，再由全体反馈推荐补足：

- 零张个人提名：八张全体反馈推荐 + 四张全新探索。
- 两张个人提名：两张提名 + 六张全体反馈推荐 + 四张全新探索。
- 四张个人提名：四张提名 + 四张全体反馈推荐 + 四张全新探索。
- 最多六张个人提名：六张提名 + 两张全体反馈推荐 + 四张全新探索。

全体反馈推荐内部同时包含“偏好学习”和“折中修复”：喜欢较多、拒绝较少的类别提高权重；多人评价为“还行”、强烈拒绝较少且地理负担更均衡的候选优先用于修复分歧。

同一地点不得跨轮重复。类别分数采用可解释的聚合信号：喜欢 `+2`、还行 `+0.5`、不想去 `-1.5`。候选仍按类别轮转发牌，避免某个高频类别占满整批。高德搜索相关性与评分只作为地点质量信号，不直接取代类别多样性。若私人卡没有提名，对应空位自动由全体反馈推荐补足，十二张共享卡的总数不变。

## 数据模型

### rooms 新字段

- `current_round`：当前轮次，默认 1，最大 3。
- `round_history_json`：已关闭轮次的摘要数组，包括候选 ID、类别、聚合反馈、换批原因、开始时间和结束时间。

### members 新字段

- `refresh_request_round`：成员请求换批的轮次；未请求为 `NULL`。
- `private_candidates_json`：当前轮该成员的三张私人救援卡；未触发时为 `NULL`。
- `nominated_candidate_json`：当前轮最多一张个人提名；未提名或全部拒绝时为 `NULL`。

现有 `choices_json` 与 `submitted_at` 表示当前轮状态。开启新一轮时，服务端在同一事务中归档当前轮、更新候选、递增轮次，并清空当前轮的 `choices_json`、`submitted_at` 和换批请求；预算、通勤、场景偏好、出发地和 AI 字段继续保留。

旧房间兼容：缺少新字段的历史房间按第一轮处理，历史为空。

## 接口与权限

新增 `/api/rounds`：

- `POST action=request`：成员携带房间号、成员 ID 和本地身份凭证，请求或取消本轮换批。
- `POST action=advance`：房主携带身份凭证、新候选与候选元数据，确认进入下一轮。
- `POST action=private-discovery`：全拒绝成员携带身份凭证，请求三张私人救援卡。
- `POST action=nominate`：成员提名一张私人救援卡，或清除自己的提名。

服务端校验：

- 请求者必须是房间真实成员。
- 换批请求必须对应当前轮。
- 只有首位创建成员可以 advance。
- 当前轮不能超过三轮。
- 当前已加入成员必须全部提交，或本轮计算结果明确为零候选。
- 新候选不能包含历史轮次和当前轮已出现的地点。
- 只有当前轮十二张共享卡全部拒绝的成员可以请求私人救援卡。
- 提名地点必须来自服务端为该成员生成的当前轮私人救援卡。

身份仍沿用现有随机成员凭证和哈希校验，不依赖 GPT 或登录账号。

## 界面状态

### 成员提交页

- 主按钮：“提交这轮选择”。
- 次要开关：“这批都没感觉，请求换一批”。
- 提交后仍可取消请求，直到房主开启下一轮。
- 若十二张全部拒绝，提交前进入私人救援步骤：显示三张仅本人可见的卡片，可提名一张或全部跳过。
- 私人卡明确标注“仅你可见 · 提名后进入下一轮共享评选”。

### 房间页

- 显示“第 1/3 轮”。
- 显示完成数与请求换批人数。
- 普通成员看到自己的请求状态。
- 房主在所有成员完成后看到“根据全体反馈开启下一轮”。
- 开启前弹出确认，说明将保留约束与反馈、清空本轮卡片选择。

### 结果页

- 有交集：继续显示三种可切换策略；房主也可选择开启下一轮。
- 零交集且轮次小于 3：主操作改为“没有交集，换一批继续选”。
- 第三轮零交集：显示具体冲突诊断，不再提供第四轮。

## 冲突诊断

第三轮无解时，系统从确定性过滤过程生成原因，不要求 AI 才能工作。至少覆盖：

- 通勤上限导致所有候选被某成员排除。
- 预算上限与已知价格不相容。
- 某成员明确拒绝全部可行候选。
- 时间窗口短于候选建议时长。
- 自然语言硬约束导致事实不足或全部排除。

界面显示最主要的一至两条冲突，并提供“调整我的边界”和“返回房间讨论”。

## 并发与失败处理

- 开启下一轮必须使用数据库事务或条件更新，防止房主重复点击生成两轮。
- advance 请求携带期望轮次；服务端发现轮次已变化时返回冲突状态，客户端刷新房间。
- 候选生成失败时保持当前轮和成员提交不变，不提前清空数据。
- 房间轮询继续同步成员完成、换批请求和轮次变化。

## 测试范围

- 所有成员同轮获得相同候选，个人通勤展示不同。
- 普通成员只能请求，不能开启下一轮。
- 房主不能在成员未完成时打断本轮。
- 单人房主完成后可以换批。
- 新一轮排除所有历史地点并保留个人约束。
- 只有全拒绝成员能获取三张私人救援卡；私人卡全部不满意时可以跳过。
- 每位成员每轮最多提名一张，提名只进入下一轮共享池，不能直接成为结果。
- 下一轮始终十二张，至少四张为新探索，其余位置按提名数动态补足。
- 全体喜欢、还行、拒绝会按既定权重影响下一批类别。
- 零结果在第一、二轮允许换批，第三轮显示冲突诊断。
- 重复 advance 请求不会跳过轮次或重复清空数据。
- 候选接口失败不会破坏当前房间。
- 旧房间按第一轮正常读取。

## 非目标

- 不在本次实现实时聊天、账号系统或无限滚动的个人私有候选流。
- 不允许未经其他成员评价的个人候选直接成为最终结果。
- 不无限生成候选；最多三轮。
- 不把 DeepSeek 作为换批、权限或冲突诊断的必要依赖。
