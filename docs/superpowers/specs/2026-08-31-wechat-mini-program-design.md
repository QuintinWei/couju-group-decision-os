# 凑局微信小程序一期设计说明

日期：2026-08-31  
分支：`feat/wechat-mini-program`  
AppID：`wx7162630074a237b6`

## 1. 目标

在不影响现有 H5 在线 Demo 的前提下，新增一套真正适合微信操作的凑局小程序前端。第一期以“可在微信开发者工具中完整体验核心流程”为交付目标，同时保留“一起吃饭”和“出去玩”两种局。

小程序不是把网页塞进 WebView，而是用 Taro、React 和 TypeScript 重写交互界面；已有房间、多人约束、候选召回、反馈学习、公平排序、DeepSeek 理解和高德地点能力继续由现有服务端提供。

## 2. 一期范围

### 包含

- 小程序首页：创建吃饭局、创建玩乐局、通过房间码加入。
- 创建房间：城市、出发地、日期范围、时段、预计时长、推荐方式、人数和可选倾向。
- 房间大厅：成员状态、房间码、微信分享和继续填写入口。
- 空闲时间：按日期填写一段或多段时间范围。
- 个人边界：预算、通勤上限和场景偏好。
- 共享卡片：12 张候选的喜欢、中立、不喜欢选择及精简的不喜欢原因。
- 无交集恢复：冲突说明、个人发现卡、可选提名和下一轮。
- 最终结果：共同方案、成员满足情况和推荐理由。
- 微信原生分享：分享当前房间，好友打开后可直接进入加入流程。
- 微信静默登录：使用 OpenID 建立凑局账号，自动恢复用户身份和昵称。
- 自动昵称：首次登录生成不重复的“微信用户 XXXX”，无需填写即可参与。
- 可选微信昵称：用户主动选择时，通过微信昵称填写能力一键替换自动昵称。
- 支持当前十座城市和现有吃饭、玩乐候选逻辑。

### 不包含

- 手机号授权和手机号账号体系。
- 微信支付、订座、购票和地图导航闭环。
- 正式提交微信审核和发布上线。
- 重写 Cloudflare D1、DeepSeek、高德或 FairMix 排序服务。
- 修改现有 H5 的交互和线上访问地址。

## 3. 技术方案

采用“同一仓库、独立前端、共享服务端”结构：

```text
couju-group-decision-os/
├── app/                    # 现有 H5 与 API，保持正常运行
├── lib/                    # 现有候选、反馈和排序逻辑
├── miniapp/                # 新增 Taro 微信小程序
│   ├── config/
│   ├── src/
│   │   ├── app.config.ts
│   │   ├── app.ts
│   │   ├── pages/
│   │   ├── components/
│   │   ├── services/
│   │   ├── store/
│   │   ├── styles/
│   │   └── types/
│   └── project.config.json
└── docs/
```

小程序通过 HTTPS 请求现有 API。服务地址由环境配置提供，不写死在页面中：

- 开发环境：指向当前在线服务；微信开发者工具可关闭合法域名校验。
- 后续正式发布：把生产 API 域名配置为微信公众平台的 request 合法域名。

微信小程序请求不依赖浏览器 Cookie。小程序先通过 `Taro.login` 获取一次性 code，服务端再使用 AppID 和 AppSecret 调用微信 `code2Session`，取得 OpenID 并签发凑局自己的登录 token。AppSecret 只保存在服务端密钥中，不进入仓库、小程序包或接口响应。

房间内仍沿用 `roomCode + memberId + memberToken` 校验成员操作，同时把成员记录关联到登录用户。这样可以保留现有房间权限边界，又能在重新打开小程序时自动恢复用户及其房间身份。

凑局 access token 使用服务端密钥签名并包含用户 id、签发时间和过期时间，有效期 30 天；服务端每次请求都验证签名和有效期。成员表新增可空的 `userId`，小程序成员写入该字段，现有 H5 匿名成员保持为空，因此 H5 无需微信登录也能继续使用。

## 4. 页面与流程

### 4.1 页面结构

| 页面 | 路径 | 主要职责 |
| --- | --- | --- |
| 首页 | `pages/home/index` | 选择吃饭局或玩乐局、输入房间码加入 |
| 创建 | `pages/create/index` | 创建局并保存房主身份 |
| 房间 | `pages/room/index` | 展示成员进度、分享房间、进入下一步 |
| 空闲时间 | `pages/availability/index` | 提交一段或多段可参与时间 |
| 个人边界 | `pages/constraints/index` | 提交预算、通勤与软偏好 |
| 共享滑卡 | `pages/swipe/index` | 对当轮 12 张共享卡反馈 |
| 个人发现 | `pages/discovery/index` | 无交集时查看 3 张私人卡并可选提名 |
| 结果 | `pages/result/index` | 显示最终结果、冲突诊断或开启下一轮 |

### 4.2 创建与分享

1. 小程序启动时静默登录；首次登录自动生成“微信用户 XXXX”。
2. 用户在首页选择局类型。
3. 创建页不再重复询问局类型，只填写该类型所需配置。
4. 创建成功后保存房主身份并进入房间页。
5. 分享卡携带房间码，例如 `pages/home/index?room=ABC123`。
6. 好友打开分享卡后自动登录，看到房间摘要，填写出发地后即可加入。
7. 用户可在个人入口主动点击“使用微信昵称”，通过 `input type="nickname"` 选择微信建议昵称；拒绝或跳过不影响使用。

### 4.3 多人决策

1. 目标成员全部加入，并分别提交空闲时间、出发地与个人边界。
2. 服务端生成所有成员均满足硬约束的 12 张共享卡。
3. 每名成员独立反馈，服务端判断是否产生共同可接受结果。
4. 有结果时进入最终结果；没有结果时展示本轮学习摘要。
5. 符合恢复条件的成员进入 3 张私人发现卡，可提名 1 张或跳过。
6. 房主在所有成员完成后开启下一轮，服务端综合提名、上一轮反馈和新类型探索生成新共享卡池。

## 5. 状态与身份

小程序本地只保存登录和继续当前流程所需的最小状态：

```ts
type Session = {
  accessToken: string;
  user: {
    id: string;
    nickname: string;
  };
};

type Membership = {
  roomCode: string;
  memberId: string;
  memberToken: string;
};
```

- 使用 `Taro.setStorageSync` 保存凑局 access token，并按房间码保存成员身份。
- OpenID 和微信 session key 只保存在服务端；小程序客户端不保存、不展示。
- access token 失效时重新执行微信登录，并恢复同一 OpenID 对应的凑局用户。
- 每次进入房间先用成员身份读取参与者视图；成员身份失效时清除该房间记录并重新加入。
- 不把其他成员的私人卡、具体空闲时间或 token 暴露到客户端。
- 页面状态以服务端房间数据为准，本地只缓存交互中的临时选择。
- 提交操作携带 `expectedRound`，沿用现有服务端的过期轮次保护。

### 5.1 用户数据

服务端新增最小用户记录：

```ts
type User = {
  id: string;
  openid: string;
  nickname: string;
  createdAt: string;
  updatedAt: string;
};
```

- `openid` 唯一索引，只用于识别同一微信用户。
- 首次登录由服务端根据用户 id 生成稳定且不重复的自动昵称。
- 微信不会在静默登录中直接返回真实昵称；真实昵称只在用户主动选择并提交后更新。
- 一期不保存微信头像，避免增加文件上传、临时路径失效和内容审核链路。

## 6. API 适配

在 `miniapp/src/services` 建立统一请求层，页面不直接拼接 URL 或身份字段。

| 能力 | 现有接口 |
| --- | --- |
| 微信登录、读取当前用户 | 新增 `/api/auth/wechat` |
| 更新可选昵称 | 新增 `/api/users/profile` |
| 创建、查询房间 | `/api/rooms` |
| 加入、提交个人边界 | `/api/members` |
| 提交空闲时间 | `/api/availability` |
| 获取或刷新候选 | `/api/candidates` |
| 提交反馈、私人提名、推进轮次 | `/api/rounds` |
| 自然语言偏好理解 | `/api/preferences` |
| AI 学习摘要与冲突说明 | `/api/insights` |
| 最终推荐理由 | `/api/explain` |
| 定位与地点解析 | `/api/location` |

统一请求层负责：

- API 基础地址与超时。
- 凑局 access token、`roomCode`、`memberId`、`memberToken` 和 `expectedRound` 注入。
- 业务错误转换为可读提示。
- 防止重复提交。
- 401/403 身份失效处理。
- 请求失败后的明确重试入口，不伪造成功数据。

### 6.1 微信登录接口

`POST /api/auth/wechat` 接收小程序的一次性 code，服务端完成以下处理：

1. 使用服务端 AppID 和 AppSecret 调用微信 `code2Session`。
2. 按 OpenID 查找或创建凑局用户。
3. 为首次用户生成自动昵称。
4. 签发有有效期的凑局 access token。
5. 只返回凑局用户 id、昵称和 access token，不返回 OpenID、AppSecret 或 session key。

同一个微信 code 只能使用一次；登录失败时小程序重新调用 `Taro.login`，不重放旧 code。

服务端新增 `WECHAT_APP_SECRET` 和 `WECHAT_TOKEN_SECRET` 两项部署密钥；AppID 可作为非敏感配置保存。任何密钥都不得写入 `project.config.json`、前端环境变量或 Git 历史。

## 7. 微信能力与降级

### 定位

- 只有用户主动点击“定位”后才请求 `Taro.getLocation` 权限。
- 定位成功后调用现有地点解析能力，同步城市与出发地。
- 拒绝授权、超时或高德失败时保留手动输入，不阻断创建和加入。
- 不把“浏览器 IP 定位”当成设备精确定位。

### 分享

- 房间页实现 `onShareAppMessage`，分享标题根据吃饭局或玩乐局变化。
- 分享路径只携带房间码，不携带成员 token。
- 二维码、朋友圈分享和正式线上域名配置不属于一期验收条件。

### 昵称

- 微信静默登录不等于取得微信昵称，界面不得声称已自动获取真实微信资料。
- 默认昵称可直接创建或加入房间，昵称输入不再是主流程必填项。
- “使用微信昵称”必须由用户主动操作，拒绝后继续使用自动昵称。

## 8. 视觉与交互原则

- 延续现有紫蓝渐变与凑局标识，但按手机单列布局重排，不机械缩小 PC 页面。
- 主要操作固定在安全区上方，适配全面屏底部区域。
- 卡片使用手势滑动与可点击按钮双通道，避免只靠手势。
- 房间进度只显示当前需要做的动作，不重复首页的四步介绍。
- 不喜欢原因使用底部半屏小面板，信息保持精简。
- 加载、空态、无交集、定位失败和服务失败使用不同状态，避免用户误以为“卡住”。

## 9. 错误处理

- 网络失败：保留当前填写内容，显示重试按钮。
- 房间不存在：回到首页并保留输入的房间码。
- 房间已满：明确提示，不创建匿名成员。
- 身份失效：清除对应房间的本地身份，允许重新加入。
- 微信登录失败：保留当前页面并提供重试，不降级为可伪造的客户端用户 id。
- 轮次过期：重新拉取房间状态，不覆盖新一轮数据。
- 候选不足：展示服务端的真实原因，不使用假卡补齐。
- 定位失败：切换为手动填写城市和出发地。

## 10. 验收标准

一期在微信开发者工具中满足以下条件即视为完成：

1. 使用 AppID `wx7162630074a237b6` 可以导入并编译小程序工程。
2. 用户首次进入可完成微信登录，且无需填写昵称即可使用自动昵称参与。
3. 同一微信用户重新进入后能恢复凑局用户身份和昵称。
4. 用户可主动一键选择微信建议昵称，跳过或拒绝不影响主流程。
5. 首页可分别创建吃饭局和玩乐局。
6. 两个模拟用户可通过房间码进入同一房间。
7. 双方可提交时间和个人边界，且未全部完成前不能提前生成共享卡。
8. 可完成一轮 12 张共享卡反馈并看到结果或无交集状态。
9. 无交集时可进入 3 张私人发现卡，选择提名或跳过，再由房主开启下一轮。
10. 分享卡打开后能带入正确房间码，且不泄露分享者身份 token。
11. 定位失败时可以手动完成流程。
12. 常用手机尺寸下无横向滚动，底部主要按钮不被安全区遮挡。
13. 现有 H5 构建和自动化测试继续通过。
