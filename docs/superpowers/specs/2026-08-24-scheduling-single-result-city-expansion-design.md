# 凑局时间协调、单一结果与十城推荐升级设计

## 目标

把“房主先决定精确时间，再让大家选地点”的流程改成真正的群体协调：房主只提供日期范围、大概时段和预计时长，成员分别提交空闲时间，系统先计算共同时间，再给出一个可执行的群体最优地点。

本次同时解决三个已确认的问题：

- 结果页只保留一个群体最优解，不再要求用户在“最佳平衡 / 最公平 / 最省事”之间二次决策。
- 固定意向时扩大高德召回并控制重复，在质量与探索之间保留随机性。
- 城市从上海、北京、广州、深圳、杭州、成都扩展为十城，新增南京、重庆、苏州、合肥。

## 产品流程

### 1. 创建房间

首页不再要求精确填写开始和结束时间，改为：

- 日期范围：今天、本周末、下周末、自定义。
- 大概时段：上午、午餐、下午、晚餐、夜间，可多选。
- 预计时长：1.5 小时、2 小时、3 小时、4 小时、不确定。
- 城市：保留原六城并新增南京、重庆、苏州、合肥。

创建摘要使用自然语言展示，例如：

> 本周末 · 下午或晚餐 · 大约 3 小时  
> 具体时间将在成员提交空闲时段后自动确定

新版上线时清空现有房间与成员数据，不兼容旧的精确时间房间。用户需要使用新版流程重新创建房间。

### 2. 成员提交空闲时间

成员加入房间后，先在日期与时间网格中选择自己可参加的区间，再进入预算、通勤和地点卡片选择。

- 自定义日期范围最多 14 天。
- 时间选择按 30 分钟粒度保存。
- 默认只展示房主选择的大概时段，成员可以展开“其他时间”。
- 每位成员可选择多个不连续区间。
- 自然语言补充可以填写“周六三点后都行、周日不要太晚”等；DeepSeek 可辅助抽取，但规则模式必须能够完成基础解析。

### 3. 计算共同时间

系统按 30 分钟滑动窗口计算可容纳预计时长的时间段：

1. 优先选择所有已加入成员都可参加的窗口。
2. 多个全员窗口并列时，依次比较房主时段偏好、成员总余量、日期先后与开始时间。
3. 若没有全员交集，不伪造最终时间；展示一个到场人数最多的候选窗口，并明确缺席成员，让房主选择调整范围或继续邀请成员修改。
4. 精确时间确定后，房间标题统一展示为 `8 月 29 日 周六 · 15:00–18:00`。

时间结果由服务端根据成员提交计算并持久化，客户端轮询只能展示服务端结果，不能自行假定时间已锁定。

## 推荐卡片升级

### 高德召回

高德评分不是唯一排序条件。系统先构造足够大的候选池，再进行质量分层和多样性抽样：

- 固定意向仍限定用户明确选择的类型，但搜索页码会根据房间轮次和换批次数在第 1–5 页之间轮换。
- 同一房间已出现过的高德 POI ID 必须排除。
- 每个意向从多个结果页召回，合并去重后再选 12 张，不直接沿用高德第一页顺序。
- 已知评分较低的地点降权但不作绝对硬过滤；缺少评分的新店仍可进入探索部分。
- 每批约 60% 来自高匹配、高质量候选，约 40% 来自同意向下的新地点或尚未探索的细分类别。
- 餐厅房间不得混入娱乐地点，活动房间不得把普通餐厅当作活动推荐。

高德接口失败或候选不足时继续使用明确标注的 Demo 数据，并遵守相同的去重和类别配额规则。

### 重复控制

- 当前轮、历史轮、私人发现被拒绝的 POI 都进入房间排除集合。
- 同品牌不同门店不视为相同 POI，但同一批最多保留一个同品牌门店，避免连锁店刷屏。
- 用户固定意向时允许类别重复，但地点必须优先换新。
- 三轮内不重复相同 POI；候选确实不足时返回可解释错误，不静默复用旧卡片。

## 单一最终结果

结果页只展示 `rankGroupCandidates` 的第一名，并命名为“群体最优解”。

- 仍先执行明确拒绝、预算、通勤、时长和忌口等硬过滤。
- 在可行候选中使用最低成员满意度、Nash 群体福利、平均满意度、通勤与价格负担计算综合排序。
- 公平度、Nash 福利、平均通勤和预算压力作为解释指标，而不是可切换的多个答案。
- 保留“锁定方案”“否决并重新计算”“没有交集则进入下一轮”。
- DeepSeek 只负责生成易懂解释，不参与授权、硬过滤或最终排序。

## 数据模型与接口

### 房间配置

新增可选字段：

- `dateRange: { start: string; end: string }`
- `preferredPeriods: Array<"morning" | "lunch" | "afternoon" | "dinner" | "night">`
- `durationMinutes: 90 | 120 | 180 | 240 | null`
- `resolvedSchedule: { startAt: string; endAt: string; attendeeIds: string[] } | null`

旧的 `date/startTime/endTime` 创建结构不再使用；最终展示时间只来自 `resolvedSchedule`。

### 成员

新增 `availability_json`，保存标准化后的 30 分钟区间。提交必须带 `expectedRound`，避免旧页面覆盖新状态。

### 服务端职责

- 新增纯函数 `resolveGroupSchedule`，负责窗口切分、全员交集、最大到场替代方案和稳定排序。
- 成员接口校验区间落在房间日期范围内、没有反向区间、总数量受限。
- 房间公开摘要不返回任何成员的具体空闲区间。
- 候选接口根据已确定时间补充营业信息提示；无法确认营业时继续标记为待确认，不声称实时可订。

### 数据迁移

- 迁移先删除现有成员记录，再删除现有房间记录。
- 删除仅发生在本次新版结构上线时；候选素材、环境变量和 API Key 不受影响。
- 新版上线后创建的房间继续按正常 D1 持久化流程保存。

## 十城支持

`SUPPORTED_CITIES` 扩展为：

- 上海、北京、广州、深圳、杭州、成都
- 南京、重庆、苏州、合肥

每座新增城市提供高德检索区域、城市中心、代表区域和 Demo 坐标。重庆因地形和道路结构复杂，直线估算仅作候选排序提示，不冒充真实路线时间。

## 错误处理

- 没有时间交集：展示最大到场窗口与冲突成员，不生成虚假全员结果。
- 空闲时间提交过期：返回 409，并刷新房间状态，保留用户尚未提交的本地选择。
- 高德结果不足：保留当前轮和所有成员提交，不创建半套卡池。
- 时间已经锁定后成员加入：新成员必须先确认该时间可参加，不能静默改变已锁定时间。

## 测试与验收

- 创建页不再要求精确开始/结束时间，能生成日期范围、时段和时长摘要。
- 多成员时间区间能计算唯一全员交集；无全员交集时返回稳定的最大到场方案。
- 数据迁移会清空旧房间和旧成员，新版房间只能使用日期范围、时段和时长创建。
- 十个城市都能生成 12 张类型正确且唯一的候选卡。
- 固定意向连续换批时不重复相同 POI，并轮换高德页码。
- 质量层和探索层均有可执行测试，缺少评分不会被直接剔除。
- 结果页只出现一个“群体最优解”，不存在三个策略切换入口。
- 完整构建、测试、Lint、迁移检查通过后，更新 GitHub main 与公开 Demo。

## 外部数据策略

本阶段继续以高德 Web Service 为地点事实来源。美团/大众点评开放能力需要企业申请与商务评估，且没有公开统一的自助 API 价格，因此不作为本次上线依赖；未来获得正式合作权限后，可作为评分、评价量和消费信息的补充来源。
