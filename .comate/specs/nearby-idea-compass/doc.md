# 附近灵感罗盘：定位城市联动与倾向候选扩展

## 背景与目标

当前创建房间页已经支持浏览器定位、手动输入地铁站/商圈、默认跨类别探索和“我有点想法”模式，但存在以下问题：

- 推荐说明卡中包含“划卡后，换一批会参考你的真实反馈。”，该句需要删除，其他推荐机制说明保留。
- 浏览器定位失败时，用户只能看到较笼统的失败提示；高德 Key 缺失、逆地理服务超时、浏览器权限拒绝和系统定位超时没有清晰区分。
- 定位成功后只保存坐标和附近标签，不会根据逆地理结果自动更新城市，导致手动城市和实际位置可能不一致。
- 一起聚餐的“我有点想法”缺少东北菜、川湘菜、江西菜和东南亚菜，并且仍显示“云南菜”；需要改成“云贵菜”。
- 周末活动的“我有点想法”没有景点选择；需要增加“景点”选项。活动候选已经通过跨类别采样控制多样性，不再额外过滤景点。

本次改造保持现有房间、候选、滑卡和公平排序架构不变，只调整推荐召回、定位返回和创建页交互。

## 需求场景与处理逻辑

### 1. 清理推荐说明文案

**场景：** 用户进入创建房间页右侧的“随机，但不是乱推”说明卡。

**处理：** 删除以下句子：

```text
划卡后，换一批会参考你的真实反馈。
```

保留：

```text
系统会控制类别多样性；位置只做附近优先。
```

以及下方三条事实说明。这样不会改变现有 `strategy=learn` 的真实反馈召回逻辑，只移除不需要展示的文案。

### 2. 定位失败可解释、定位成功自动切换城市

**场景 A：浏览器定位成功。**

1. 浏览器通过 `navigator.geolocation.getCurrentPosition` 获取 GPS 坐标。
2. 前端将坐标发送到 `/api/location`。
3. 服务端调用高德坐标转换和逆地理编码，继续返回降低精度后的 `location` 和附近标签 `label`。
4. 服务端从逆地理结果的 `city` / `province` / `district` 中识别六个已支持城市之一，并返回 `city` 字段。
5. 前端收到 `city` 后自动更新 `config.city`；如果识别出的城市与当前城市不同，则城市下拉框同步切换，并在状态提示中明确说明“已自动切换到 X”。
6. 同时保存定位坐标和附近标签，后续候选搜索使用该坐标做附近优先，房间创建使用同一坐标，避免再次用旧城市对旧地点文本做地理编码。

建议的返回形状：

```ts
{
  location: { lng: number; lat: number },
  label: string,
  city: CityName | null,
  mode: "device"
}
```

**场景 B：定位成功但不在六个支持城市内。**

保留坐标和“当前位置附近”标签，不强行把城市改成错误城市；`city` 返回 `null`，前端保留用户当前城市并提示“已定位，但暂未识别到支持城市，仍使用当前城市”。候选接口仍可使用坐标进行附近优先，但不伪造城市归属。

**场景 C：没有高德 Key 或高德逆地理服务暂时不可用。**

浏览器坐标本身仍是有效定位结果，因此服务端采用安全的坐标兜底：返回经四位小数处理的坐标、通用标签“当前位置附近”和 `city: null`，不调用外部服务时不自动切换城市。这样用户仍可以创建房间和体验候选，不会因为逆地理服务不可用而整体定位失败。

**场景 D：浏览器定位失败。**

根据 `GeolocationPositionError.code` 给出可操作提示：

- `PERMISSION_DENIED`：提示用户在浏览器站点权限中允许定位，并提供手动输入地铁站/商圈的替代路径。
- `POSITION_UNAVAILABLE`：提示系统定位服务或网络暂时不可用，可重试或手动输入。
- `TIMEOUT`：提示定位超时，可重试或手动输入。
- 其他情况：提示暂时无法获取位置，可手动输入。

加入房间页仍使用房间已有城市，不自动改变房间配置；但加入者的定位失败提示也应区分权限、不可用和超时，避免所有错误都显示为“未授权定位”。

**手动输入边界：** 用户编辑出发地时继续清空旧坐标，防止旧定位坐标和新地点文字混用。用户手动切换城市时继续清空旧坐标，并保留“请重新输入或使用定位”的提示。

### 3. 扩展“我有点想法”的聚餐倾向

聚餐兴趣白名单调整为：

```ts
["本帮菜", "日料", "火锅", "烤肉", "粤菜", "西餐", "东北菜", "川湘菜", "云贵菜", "江西菜", "东南亚菜", "素食", "Brunch", "小酒馆"]
```

处理要求：

- 删除“云南菜”标签，改为“云贵菜”。
- 增加“东北菜”“川湘菜”“江西菜”和“东南亚菜”。
- 实时高德搜索直接使用这些兴趣作为关键词。
- 演示候选库增加对应的东北菜、川湘菜、云贵菜、江西菜和东南亚菜候选，避免用户选择新倾向后回退成与所选类型无关的候选。
- 保留现有餐饮类型过滤、价格和辣度排序逻辑。

### 4. 增加周末活动的景点倾向

活动兴趣中增加一个选项：

```text
景点
```

处理要求：

- “景点”作为活动兴趣白名单的一部分，在“我有点想法”中可被用户主动选择；用户展示名称只使用“景点”。
- 默认“给我灵感”继续使用现有跨类别分桶采样。景点只是其中一个可能的类别，不会因为新增选项而让整批候选都变成景点。
- 普通活动结果不再额外执行景点过滤；当前算法已经通过兴趣分桶轮询和候选数量控制类别多样性，不需要再根据 POI 名称排除景点。
- 演示候选增加至少一个类型为“景点”的候选；用户选择景点时，focused 召回应优先返回该类型，不能因为没有足够数量而静默改成完全无关的单一类别。
- 景点候选仍使用现有候选模型和排序链路，不新增数据库表或独立推荐系统。

## 架构与技术方案

### 现有架构

```text
app/page.tsx
  ├─ 创建页表单、浏览器定位和城市状态
  ├─ /api/location：定位与逆地理请求
  ├─ /api/candidates：候选召回与多样性采样
  └─ /api/rooms：使用已解析坐标创建持久化房间

lib/amap.ts
  ├─ geocodeOrigin：手动地点转坐标
  ├─ locateFromBrowser：GPS 坐标转换与逆地理编码
  └─ 坐标精度处理

lib/couju.ts
  ├─ 城市与兴趣白名单
  ├─ 演示候选模板
  └─ 候选类型与 FairMix 排序模型
```

### 关键实现策略

1. 由 `lib/amap.ts` 负责从高德逆地理响应中提取支持城市；不把高德原始行政名称直接交给前端作为城市值，避免破坏 `CityName` 类型和城市白名单。
2. `/api/location` 透传 `city`，并在 Key 缺失或逆地理失败时返回经精度处理的 GPS 坐标兜底；手动地点解析仍保持失败即要求换地点的行为。
3. `app/page.tsx` 的创建者定位成功回调根据 payload.city 更新 `config.city`，而不是调用普通的城市变更处理，避免自动切换城市时把刚刚取得的坐标清空。
4. `lib/couju.ts` 同时维护可选兴趣白名单和演示模板；活动继续使用现有跨类别兴趣池和轮询采样控制多样性，不把景点作为需要特殊过滤的类别。
5. `app/api/candidates/route.ts` 移除按 POI 名称排除景点的特殊分支，保留跨兴趣分桶、数量上限、`avoid` 和 `exclude` 机制。
6. 不把 API Key 写入源代码、`README.md` 或测试；继续使用现有本地 `.env.local` 配置。

## 数据流

### 浏览器定位与城市联动

```text
浏览器权限
  → navigator.geolocation
  → POST /api/location { lat, lng, city }
  → lib/amap.locateFromBrowser
      → 坐标转换（可选）
      → 逆地理编码（可选）
      → 匹配 SUPPORTED_CITIES
  → { location, label, city }
  → app/page.tsx 更新 creatorLocation / creatorOrigin / config.city
  → GET /api/candidates?city=...&location=lng,lat
  → POST /api/rooms 使用同一坐标
```

### 倾向候选

```text
CreateScreen 选择场景
  → 展开“我有点想法”
  → 选择兴趣
  → GET /api/candidates?interests=...
  → 服务端白名单校验
  → 高德按关键词分桶，或演示模板过滤
  → 所有活动兴趣使用同一套跨类别采样，不再按名称特殊过滤景点
  → 候选进入既有滑卡、成员反馈和 FairMix 排序
```

## 边界条件与异常处理

- 仅允许 `SUPPORTED_CITIES` 中的城市写入 `RoomConfig.city`；高德返回的“北京市”等名称必须规范化为“北京”。
- 高德返回城市为空、城市不在六城范围、字段是数组或行政名称带“市”时，不自动猜测城市，返回 `city: null`。
- 坐标仍需经过经纬度范围检查；无效坐标不得覆盖当前有效位置。
- 定位回调中的网络错误、HTTP 非 2xx、逆地理响应无效和 API 超时都必须结束 `locating` 状态，不能让按钮永久显示“定位中”。
- 自动切换城市后不能清空刚刚保存的 `creatorLocation`；手动切换城市仍然清空旧坐标。
- “景点”只是一个普通活动兴趣，和其他活动类型走同一套召回与多样性逻辑；不得把整批活动候选强制变成景点。
- 选择东北菜、川湘菜、云贵菜、江西菜或东南亚菜后，演示模式优先返回对应类型的候选；无匹配时不得静默显示完全无关的候选。
- API Key 只从环境变量读取，绝不写入代码、测试快照、README 或响应内容。

## 预期结果

- 创建页说明卡不再出现“划卡后，换一批会参考你的真实反馈。”。
- 用户定位成功且位于上海、北京、深圳、杭州、成都或广州时，城市下拉框自动切换到识别城市，坐标和附近标签继续生效。
- 定位权限拒绝、定位超时、系统不可用和高德服务异常时，用户能看到对应原因，并可继续手动输入或重试。
- 聚餐“我有点想法”显示东北菜、川湘菜、云贵菜、江西菜和东南亚菜，不再显示云南菜。
- 周末活动“我有点想法”显示“景点”，且默认跨类别推荐不会被景点垄断。
- 新兴趣在高德实时和演示模式下都能进入候选召回。
- 现有房间创建、成员加入、滑卡反馈、换一批和公平排序行为不被破坏。
